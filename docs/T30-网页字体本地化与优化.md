> 对应任务清单第 5 项：「全面优化 App，并在 App 上使用网页端字体显示，可以直接将字体打包进安装包」。
> 版本：`0.0.14+14`（versionCode 2014）。

## 一、问题有多大（真机同构实测）

用与 App WebView 相同的 UA / 视口在真实站点上量了一次「一次首页加载的字体流量」：

| 文件 | 大小 |
|---|---|
| `tianheng/TH-Tshyn-P1.woff2` | **7.88 MB** |
| `tianheng/TH-Tshyn-P0.woff2` | **5.82 MB** |
| `klee-one/KleeOne-Regular.woff2` | **2.86 MB** |
| Sarasa UI SC 子集（Regular/SemiBold/Bold/Light + extra） | 1.87 MB |
| FontAwesome（solid/regular/brands） | 0.30 MB |
| Boxed、其余 | 0.03 MB |
| **合计** | **≈ 19.2 MB** |

交接文档里「站点已子集化 ⇒ App 流量已大降」的结论**不成立**：
子集化只覆盖了 Sarasa，而字体栈是
`'Sarasa UI SC','PingFang SC','Microsoft YaHei','TH-Tshyn',sans-serif` ——
Android 上既没有 PingFang 也没有雅黑，**`TH-Tshyn` 就是实际兜底面**；
只要页面上出现一个 Sarasa 子集没覆盖的字符，浏览器就去下载那个 5–8 MB 的分片。

### 站点侧已同步「减肥」：19.2 MB → 3.9 MB（-80%）

2026-09-14 顺带把站点自身的字体流量也压了下来（对所有访客生效，不只 App）：

| 改动 | 效果 |
|---|---|
| 去掉两条 `<link rel=preload as=font>` | 19.19 → 4.94 MB。预加载是扫描器发起、JS 拦不住的，而预加载窗口里 Sarasa 尚未就位会先回退到 `TH-Tshyn` —— 去掉后它根本不会被选中，13.7 MB 直接消失 |
| Klee One 子集化（语料 = 站点正文 + GB2312 一二级 + JIS 第 1 水准 + 假名/标点） | 4.94 → **3.90 MB**；250+ 条新一言实测**完全覆盖 100%**，缺字率 0/4859 |

细节与回滚方式：主题仓库 `docs/字体子集化与预加载.md`；
原文件保留在服务器 `uploads/ybh-fonts/klee-one/KleeOne-Regular.full.woff2`。

## 二、方案：把字体打进 APK，用 `data:` URI 顶掉站点规则

`lib/src/data/embedded_fonts.dart` 三步走（顺序不能换）：

1. **闸门（hold）**：页面一开始加载就注入
   `*:not(#a):not(#b):not(#c){font-family:<占位族>!important}`。
   `@font-face` 只在「有元素用到该族」时下载，没有需求就没有请求。
   > ⚠️ 选择器必须是 `*:not(#id)…` 这种**带 id 的形状**：站点自定义 CSS 里有若干
   > `font-family:…!important`（`.header-info p{Klee One}`、`.center-text{Boxed}`），
   > 同层 `!important` 比特指度，`body *`(0,0,2) 输给 `.header-info p`(0,1,1)。
   > 实测漏的正是这两条。
2. **删掉站点的 `@font-face` 规则**：样式表与页面同源，`sheet.cssRules` 可读可写。
   凡 `src` 落在 `/ybh-fonts/` 下的规则**整条删除**：打包过的稍后补回，
   没打包的（TH-Tshyn、Sarasa J/K/HC/TC 全量族）就此消失，渲染回退系统字体。
   > ⚠️ 必须先把 `url()` 解析成绝对地址 —— FontAwesome 的 `all.min.css` 写的是
   > `url(../webfonts/fa-solid-900.woff2)`，字符串里根本没有 `ybh-fonts`。
3. **插入内联规则并放开闸门**：一条 `<style>`，`src` 用 `data:font/woff2;base64,…`，
   `font-family / weight / style / unicode-range` 与站点规则逐条对应
   （描述符在构建期从站点 CSS 解析进 `assets/fonts/manifest.json`），然后移除闸门。

### 打包清单（`assets/fonts/`，16 个文件 / 5.38 MB）

```
slice/SarasaUiSC-{Light,Regular,SemiBold,Bold}.{subset,extra}.woff2   8 个  2.47 MB
slice/LXGWWenKai-Regular.{subset,extra}.woff2                         2 个  1.01 MB
klee-one/KleeOne-Regular.woff2  ← 子集：站点正文 + GB2312 一二级 + JIS 第 1 水准
                                  + 假名/标点（250+ 条新一言实测覆盖 100%）  1.83 MB（原 2.86 MB）
fontawesome/webfonts/fa-{solid-900,regular-400,brands-400}.woff2      3 个  0.30 MB
Boxed-Regular.woff2                                                    1 个  0.03 MB
empty.woff2 / manifest.json                                            2 个
```

**未打包**（体积换收益不划算，规则会被删掉，回退系统字体）：
`TH-Tshyn` 四个分片共 **29 MB**、`Sarasa UI J/K/HC/TC` 全量族共 **300+ MB**（换肤用，从不下发）。

### ⚠️ 一个需要下一轮决策的代价：内联 CSS 有 11 MB

`data:` URI 方案要把字体 base64 内联进一段 CSS，**每次导航**经 `runJavaScript` 送进页面。
5.38 MB 字体 → **11.08 MB CSS 字符串**（实测）。真机上这笔开销是 CPU/内存而非流量，
但每次翻页都要付一次。

站点侧「减肥」后（19.2 → 3.9 MB），这笔账的性价比已经变了，下一轮建议二选一：

1. **Cache Storage 持久化**（推荐）：首次导航注入一次并写入 Cache Storage，
   后续导航读缓存生成 blob URL —— 传输只付一次。JS 逻辑可在浏览器里用
   `font_app_verify2.js` 的两段式导航验证，不必等真机。
2. **只打包核心面**：Sarasa 400/600/700 + FA + Boxed + Klee One（≈4.0 MB → 5.4 MB CSS），
   把 Light 与 LXGW WenKai 交回网络（它们只在个别页面/斜体时用到）。
   代价是这两者出现时会有网络请求，「0 请求」不再是结构性保证。

当前保留全量打包，是因为**它至少是可解释的**：0 网络请求、断网可用。

## 三、走过弯路（避免后人重踩）

| 方案 | 结论 |
|---|---|
| **往 `<head>` 追加同名 `@font-face` 覆盖** | ❌ 无效。Chrome 对同族同字重同字形取**最先声明**那条，追加在后面不生效（真实页面 A/B 验证过） |
| **改写 CSSOM 里已有规则的 `src`** | ❌ 无效。Chrome 不会为被改写的 `CSSFontFaceRule` 重建 FontFace：原字体不再下载（看着像成功），新字体也永不加载，整页静默退回系统字体。必须**删旧规则 + 插新规则** |
| **本机 HTTP 服务 `http://127.0.0.1:port`** | ❌ 无效。https 公网页访问回环地址受 **Local Network Access** 管辖，浏览器直接拒绝：`Permission was denied for this request to access the 'loopback' address space` —— **请求根本不会发出**（服务端一个包都收不到），加任何 CORS / `Access-Control-Allow-Private-Network` 头都无用 |
| **等到 `DOMContentLoaded` 再放开闸门** | ⚠️ 太晚。本站同步脚本多，实测 DOMContentLoaded 要 3 秒后才到，用户会盯着系统字体看 3 秒。改为「样式表数量连续 8 拍不变」即放开（≈0.7–0.9 秒） |
| **站点侧字体 `<link rel=preload as=font>`** | 预加载扫描器发起，页面 JS 无法取消 ⇒ 已在主题 v1.3.2 去掉（见下） |

## 四、站点侧配合（主题仓库）

1. **去掉字体预加载**（`inc/ybh/bootstrap.php::ybh_resource_hints()`）：
   `<link rel=preload as=font>` 由预加载扫描器发起、页面 JS 无法取消，
   是客户端字体本地化**唯一无法在客户端修补的漏点**；
   子集化后两个字重合计 0.88 MB，收益已不抵无条件下载的代价。
2. **构建期语料**：`assets/fonts/manifest.json` 的描述符由站点 `css/ybh.css`
   与 FontAwesome `all.min.css` 解析而来；站点换字体后需要重跑一次生成脚本。

### 6.1 构建受阻的完整记录（留给下一轮）

| 现象 | 原因 / 对策 |
|---|---|
| **`gradlew` 只打印一行 `... single-use Daemon process will be forked` 就退出 1，**毫无错误信息**，`~/.gradle/daemon/*/daemon-*.out.log` 也不生成 | ⭐ **本机同时导出了 `http_proxy` 与 `HTTP_PROXY`（https/no_proxy 同理）。这对大小写重复的环境变量会让 Windows 上 fork 出来的 JVM 直接以 `0xC0000005`(BEX64) 崩掉。** 事件日志可证：`Faulting application name: java.exe ... Exception code: 0xc0000005, Event Name: BEX64, Faulting module: unknown`。**开跑前 `Remove-Item Env:http_proxy,Env:HTTPS_PROXY,...` 清掉它们，问题消失** —— 清掉后 `gradlew --debug help` 直接 `BUILD SUCCESSFUL in 1m 30s` |
| 同一个坑的第二个症状 | 清掉之前 `Start-Process` 会抛 `Item has already been added. Key in dictionary: 'HTTP_PROXY'`（PowerShell 环境字典大小写不敏感）；清掉后 Start-Process 正常，可用来起**脱离调用方**的长任务 |
| `flutter build apk` / `flutter.bat` 无输出即崩 | 原版 `flutter.bat` 会先 `CALL bin\internal\shared.bat`（git 探测）再链式执行 dart。已把它替换为只调用 flutter_tools snapshot 的 shim，原文件存为 `flutter.bat.orig` |
| 构建走到 `:app:compileFlutterBuildRelease` 才失败 | 该任务调用 `flutter.bat`，正是上面那个崩点。Gradle 的报错很明确：`Process 'command 'flutter.bat'' finished with non-zero exit value -1073741819 (NTSTATUS 0xC0000005)` |
| 不加 `--foreground` 守护进程一起就死；加了又卡死 | **`--foreground` 是死路**：jstack 显示它只停在 `Daemon.awaitExpiration`，压根没收到构建请求。别再用它 |
| Gradle 直接调用时凭空出现 CMake 报错 | 缺 `-Pflutter.androidSdkRoot` / `-Pflutter.installedNdkVersions` 时，Flutter Gradle 插件会走 `configureSyntheticExternalNativeBuildFallback`，建一个**空 CMake 工程**只为骗 AGP 下载 NDK。补上这两个 `-P` 参数即可跳过 |
| `gradle.properties` 的 `-Xmx8G` | 可用内存 < 8G 时守护进程被系统杀掉，同样是「无输出 BUILD FAILED」。已压到 2G/768m |

**✅ 已解决（2026-09-14 05:00）**：上表全部成立，另补两条实测结论后构建一次通过
（`BUILD SUCCESSFUL in 3m 6s`）：

- `:app:compileFlutterBuildRelease` 的**随机** `0xC0000005` 用「把重试放进 shim」解决 ——
  Gradle 只要看到 `flutter.bat` 返回非零就整包失败，所以在 shim 外面重试已经太晚；
  `flutter_shim.ps1` 现在对 NTSTATUS 类的负数退出码自动重试（最多 60 次，只重试崩溃、不掩盖真实报错）。
- `:app:minifyReleaseWithR8` 是**另一个独立的内存瓶颈**：1.5G 堆会在这一步被杀，
  堆必须 ≥ 2560m（已写入 `android/gradle.properties`）。
- `android/local.properties` 的 `flutter.versionCode` **缺省是 1**，不显式写会导致
  `INSTALL_FAILED_VERSION_DOWNGRADE`。脚本按 `2000 + pubspec build number` 写入，
  与 CI `--split-per-abi` 的 arm64 产物版本号对齐。

现在跑 `powershell -File tool\build_apk.ps1` 即可（自动清变量、装 shim、推导版本号、失败重试）。
